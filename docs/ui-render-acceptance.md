## 4. 图表的数据来源与诚实性

- `FaTrendChart` 只吃 `GET /api/body-records` 窗口内的真实记录：点 = `{ measuredAt → x, weightKg → y }`，
  标签 = 服务端推导的 `businessDate`。**没有**任何插值、补点、平滑。
- 横轴按**时间戳**定位（不是记录序号），所以补录造成的空档在图上就是空的。
- 只有 1 个点时只画点不连线，并在图下写"窗口内只有 1 次测量，只画点不连线"；0 个点画空状态而不是 0。
- y 轴标注直接写窗口内真实最高/最低值，不做"好看的整刻度"。
- 首页"本周"点阵画的是**计划安排**，卡片上明写"这是计划，不代表实际练过"。
- **明确未做**：组数/时长完成度进度环、训练日历已练点阵、本周场次柱状图。
  原因：`workout_session/entry/set` 与 metrics 在 V1–V22 迁移中不存在，也没有统计接口
  （阶段 2 未实施，`docs/feature-audit-before.md` §4）。提示词 §7 要求"没有对应统计接口时使用已有真实记录能支持的展示"，
  本轮就只落地了体重折线这一个。

## 5. 仍然没有证明的（请在微信开发者工具里逐条看）

1. **图标是否真的显示**：base64 SVG 走 `background-image`，微信端理论支持，但我这边无渲染证据——
   首页四宫格、我的页入口、tabBar 四处是最快的判定点。
2. **canvas 是否真的画出线**：需要 dev 库里至少 2 条体重记录（我的 → 体重 → 记录 三条不同日期）。
   看不到线但数字正常，就是 canvas 侧的问题，把控制台报错发我。
3. **点击链路**：主卡 → 计划详情、条选切日、更多菜单里每个动作、编辑页保存与冲突、体重行内展开、
   教练页发送/停止/折叠展开、导入 preview→confirm。
4. **留白与不拥挤**：320–375px 窄屏下 `FaSegmented`（动作字典 4 项带图标、体重页 4 段）是否被挤成两行；
   底部固定条是否压住内容、键盘弹起时教练页输入框是否可用（`adjust-position` 未特殊处理）。
5. **状态不只靠颜色**：选中态描边、错误横幅图形 + 文字、休息日横线 vs 有安排实心点。
6. **真机**：`127.0.0.1` 在手机上打不通，需要把 `VITE_API_BASE_URL` 换成局域网地址或只看模拟器。

## 6. 本轮引入的风险点（我自己知道的不满意项）

- `check:theme` 的图标名扫描只看**静态** `name="…"`/`icon="…"`，动态绑定（`:name="heroIcon"`）靠 TS 类型兜。
- 图标 135 条规则让 `app.wxss` 涨到约 71KB（整包仍远低于 2MB 上限，但这是"全站可用"换来的代价）。
- `FaTrendChart` 用 `canvas type="2d"`，是微信端能力；H5 端拿不到 node 句柄，图表不渲染（文字口径仍在）。
- 底部安全区用 `calc(20rpx + env(safe-area-inset-bottom))`，sass 与构建都通过，但**没在真机刘海屏上验证过**。
- `pages/coach/chat` 升为 tab 页后，任何用 `navigateTo` 跳它的代码都会静默失败——已按 `TAB_PAGES` 分流，
  后续新增入口必须走同一条路径。
